# Plan: mentioning clubs in the league's social posts

**Written 15 Sep 2026. Facebook measured and largely settled 16 Sep 2026** — see *What was
measured* below, which replaces most of what the original draft guessed at. Instagram
phases 1 and 2 are still unbuilt and unaffected.

The ask is "implement the mentions API". Researching it turned up that **there is no such
thing — there are three separate mechanisms**, they behave differently, and they are not
equally worth doing. One is nearly free, one is moderate, and one turns out to be closed to
us. This plan says which is which so the session that picks it up does not start with the
hard one.

---

## What we have today

| | Facebook | Instagram |
|---|---|---|
| Result post | no mentions | no mentions |
| Weekly tables | no mentions (**correctly so** — see below) | **caption @mentions, live** |

The weekly tables Instagram caption already names every club whose handle we hold, built
from `Club.getInstagramHandles()`. That landed on 15 Sep and is the only mention of any kind
the league currently posts.

`controllers/weeklyTablesController.js` deliberately omits mentions from the *Facebook*
message rather than faking them. That was written as a judgement call and is now a measured
one: a `@Club Name` string in a Facebook message tags nothing at all.

`models/fixture.js` carries a comment referring to `Fixture.getResultMentions` and
`getClubSocialHandlesByTeamName`. **Both functions are already deleted** — the comment is
archaeology from the quick-results-entry flow removed in `74c52d1`. Don't go looking.

## The three mechanisms

### 1. Instagram caption @mentions — cheap, works, do this first

A bare `@username` in a caption becomes a real mention and **the account gets a
notification**. No extra permission, no coordinates, works on every media type including
carousels.

Already proven on the weekly tables. The gap is that **result posts carry none**, and a
result post is the obvious place for one: exactly two clubs are involved and both would
plausibly want the notification.

### 2. Instagram `user_tags` — moderate, and only on single images

Tags an account *on the photo itself*, the way a person tags someone in a picture, rather
than in the text.

```json
user_tags: [{ "username": "ghapbadminton", "x": 0.4, "y": 0.6 }]
```

- `x` and `y` are **required for images**, 0.0–1.0 from the edges.
- **Not supported on carousels or carousel children.** So this is available for result posts
  and unavailable for the weekly tables, permanently.
- Optional for stories; supported on reels.

The result card is generated by us at a known 1080×1350 layout, so sensible coordinates are
computable rather than guessed — the home and away team names sit at known offsets in
`socialController.resultImage`.

### 3. Facebook page mentions — **closed to us**, and the measurement is below

Do not build this. The short version: mentioning another Page needs the **Page Mentioning
feature**, that feature requires App Review *and business verification*, and developers who
have been through that are reporting on Meta's own forum that it has been broken since
January 2026 anyway.

## What was measured, 16 Sep 2026

All against the live Graph API with the league's own Page token. Every test post was
`published=false` unless stated, and every one was deleted.

### A Facebook mention is not `@`-syntax at all

Two posts on our own page, three weeks apart, make the point from both sides:

| | 9 Mar 2024 (edited by hand) | 30 Mar 2024 (Make, untouched) |
|---|---|---|
| message text | `… co.uk Shell Badminton Club  Alderley Park …` | `… co.uk @Shell Badminton Club @Alderley Park …` |
| `message_tags` | **8 × `type: page`** + hashtags | hashtags only |

The `@` is *absent* from the tagged one. A real mention is plain display-name text plus a
separate `{id, name, type, offset, length}` record. Make's `@Club Name` is a literal string
that tags nothing — it had been posting those for years.

Both halves are positive observations (tags present here, literal `@` present there), which
is why this one is safe to rely on. Contrast the retracted Facebook dev-mode finding in
CLAUDE.md.

### Writing a mention: five causes tested, five closed, one left standing

`@[page-id]` in `message`, posted through the API, **applies nothing**. The interesting part
is the failure mode: the `@[…]` token is **consumed, not ignored** — the stored message came
back with an orphaned space where the mention had been. Facebook parses the syntax and then
drops it.

A silent strip is a negative observation, so it was worth ruling the alternatives out rather
than concluding from the first result:

| Candidate cause | How it was closed |
|---|---|
| The page ids are wrong | 7 of them were **harvested from Meta's own applied tags** on our posts (table below) |
| The feature only works on pages we have a role on | Tameside — which we manage — was stripped in the same post as a club |
| `published=false` doesn't resolve mentions | A genuinely **published** post (`is_published: true`) stripped it too |
| The syntax was deprecated | Identical result on **v21.0, v19.0, v17.0, v15.0, v12.0, v10.0 and v8.0** |
| "Ready for testing" means inert once the app is Live | **No** — `pages_manage_posts`, `pages_read_engagement` and `pages_show_list` all show that status *and* are working (usage 18 / 85 / 96) |

What survives is that **the Page Mentioning feature is not granted to our app**, and Meta's
own feature reference says what that costs:

> *"This permission or feature requires successful completion of the App Review process
> before your app can access live data."*
> *"This permission or feature is only available with business verification."*

### Permissions and features are not the same thing, and that is the reusable lesson

This is what made the earlier guesses wrong, twice.

- A **permission** at "Ready for testing" works on pages you administer, without review.
  That is the whole of our current posting setup.
- An **ungranted feature** is inert, whatever the dashboard says next to it.

There is a control for that claim sitting in the same app: **Page Public Content Access** is
also a feature we don't hold, and its absence is directly observable — `GET /{club-page-id}`
and `GET /{page-id}/feed` both answer `(#10)`. Two ungranted features, two inert
capabilities. The only difference is that PPCA fails **loudly** and Page Mentioning fails
**silently**.

So no amount of re-minting the Page token reaches this. **The original draft of this plan
said mentioning needs `pages_manage_engagement`; that is wrong** — that permission covers
comments and reactions, and adding it would have been a wasted trip through the login
dialog.

### Even with the feature, it may not work

[developers.facebook.com/community/threads/340829985443641](https://developers.facebook.com/community/threads/340829985443641/)
— multiple developers, from late January 2026, reporting that mentions resolve to the page
*name* but produce no actual tag or link. No Meta response, no resolution, last activity
April.

**Their failure mode is one step further along than ours**: they get the name substituted
and no link; we get the token removed entirely. The most economical reading is that they
hold the feature and we do not — which, if right, means App Review buys us their bug rather
than a working mention.

Scanning **1,595** page-authored posts for `message_tags` yields every club page we have
ever tagged. This is what phase 3 originally said to look up by hand, and it needs no Page
Public Content Access because the tags are on **our own** posts:

| College Green | `269550050189407` | |

| G.H.A.P | `245774382722600` | |

Two more were supplied by hand and are **unverified**: Aerospace `61576463475674` (already
in `club.facebook`) and Remnants `61575140378706`. Both answer `(#100) Unsupported get

in a `facebookPageId` column on the strength of the number alone.**

### Two smaller things worth keeping

- **`/{page-id}/feed` is gated, `/{page-id}/posts` is not**, on the same token. `/feed`
  includes visitor posts, which needs PPCA; `/posts` is page-authored only. The gate is the
  edge, not the permission — an easy hour to lose.
- **A Page token reads its own history cheaply.** 1,595 posts in 16 pages of results. Any
  question of the form "what have we actually been posting" is answerable in a minute.

## Recommended order

### Phase 1 — Instagram mentions on result posts

Small, self-contained, no new permissions. **This is the whole of the remaining value.**

- Add a model function alongside `Club.getInstagramHandles()` that resolves **two team
  names** to their clubs' Instagram handles. Team → club is already joinable; the roster and
  fixture models both do it.
- Append the mentions to the result caption in `publishResultToMeta`
  (`models/fixture.js`). Facebook's `message` and Instagram's `caption` are already separate
  strings there, so this touches only the Instagram one.
- A club with no handle is simply absent — never guess, never fall back to a name with an `@`
  in front. The Make scenario posted literal `@Shell Badminton Club` into Facebook messages
  for years and it did nothing, which is now measured rather than suspected.

**Test:** assert the caption contains both clubs' stored handles and no `@` for a club
without one, the same shape as `weekly-tables-post.test.js`.

### Phase 2 — Instagram `user_tags` on result posts

Only worth doing after phase 1 is live, and only if the caption mentions turn out to be
worth more than the effort.

- `metaPublisher.publishInstagramPhoto` needs to pass `user_tags` through to
  `createContainer`. Carousels must reject it rather than silently dropping it — an
  unsupported parameter that Meta ignores is exactly the failure mode this codebase keeps
  finding.
- Coordinates from the known card layout, not magic numbers: derive them from the same
  constants `resultImage` uses to place the team names.

### Phase 3 — Facebook: **don't**, and here is the trigger to revisit

The recommendation is to stop. The cost is App Review plus business verification; the
evidence is that developers who cleared both are reporting it broken and unanswered since
January.

Revisit only if **both** of these change:

1. The community thread (or a successor) shows Meta acknowledging and fixing it.
2. Somebody actually wants it — no club has asked, and Instagram already gets the
   notification.

If it is ever picked up, the order is unchanged and step 3 is the one that matters:

1. Apply for the **Page Mentioning** feature. Business verification first.
2. Put the harvested ids in a new `club.facebookPageId` column with a migration — do **not**
   overload `club.facebook`, which the club page and the JSON-LD `sameAs` both read as a
   profile URL. Verify Aerospace and Remnants before trusting them.
3. **Post one test result mentioning exactly one club, then read it back** with
   `GET /{post-id}?fields=message,message_tags` and check `message_tags` is populated.
   Nothing else distinguishes a mention from a silent strip. `published=false` makes this
   free — the post is never visible, and it strips or tags identically to a published one,
   which is itself now measured.
4. Expect a mixed result even then: **the mentioned Page must have "Others Tagging this
   Page" enabled**, which is a setting on each club's page. We cannot read it or change it.

**Decide after step 3, not before.** A feature that works for two of six clubs and fails
invisibly for the rest is worse than none, because nobody will ever notice which is which.

## Things worth carrying in

- **Read the post back.** Both platforms accept a post and then quietly do less than asked —
  Facebook strips mentions, Instagram ignores unsupported parameters. `message_tags` on the
  published post is the only honest confirmation, and it is cheap.
- **A silent strip needs its alternatives ruled out.** The first run here produced 0 of 9 and
  a tempting conclusion; four of the five candidate causes took one test each to close, and
  the one that looked most obvious — "Ready for testing" — was refuted by three permissions
  showing the same status while working.
- **Never fabricate a handle.** If a club has none, the post has no mention for that club.
  `utils/socialLinks.js` already encodes this rule for profile links: anything not
  handle-shaped returns null rather than a guessed URL.
- **`club.facebook` is overloaded already** — mostly usernames, one probable page id. A
  proper `facebookPageId` column is part of phase 3 if phase 3 ever happens.
- **Coordinates and layout constants belong together.** If phase 2 happens, the x/y values
  and the SVG offsets that place the team names must come from one place, or they will drift
  the first time the card is redesigned.
