# REARCH-08 — tests that run against a real Postgres

**Size:** M · **Window:** in-season OK (tests and tools only)
**Blocked by:** nothing. Soft: HARD-32 (migration tracking), since both touch how a
database is built from `migrations/`.
**Owns:** a new `tools/query-snapshot.js`, a new `__tests__/db/` Jest project, a
synthetic seed (`tools/local-db/test-seed.sql` or a generator), a Postgres step in
`cloudbuild.yaml`.
**Source:** the 24 Oct 2026 "build it from scratch" review.
**Needed by:** REARCH-01, REARCH-02 and REARCH-03 — this is their safety net. Do part 1
first.

## Why

37 test files mock `db_connect`. A mocked database answers whatever the test author
believed the database would answer, so every bug that lives in the gap between SQL and
reality passes. CLAUDE.md records them:

- **`{ insertId: 42 }`** — a mock inventing MySQL's shape let submitted scorecards
  redirect to `/undefined` behind a green test (gotcha 2b);
- **folded aliases** — "a mock spelling the key camelCase passes against the bug"
  (gotcha 1);
- **`[, info]`** — always `undefined` against Postgres, fine against a mock (gotcha 2d);
- `sendResultZap` — "a function that is only ever mocked is untested, however many tests
  mention it".

The real database exists now (HARD-13: `tools/local-db.sh`, Postgres 17 in Docker,
matching production's 17.6). The Playwright suite already uses it. Jest does not, and CI
has no database at all — `cloudbuild.yaml` runs Jest with mocks, and Playwright not at all.

## Three parts, each useful alone

### Part 1 — the snapshot harness (a tool, local only)

`tools/query-snapshot.js <model>.<function> --args args.json --out snap.json [--compare
snap.json]`. Runs a model function against the **local** database with each argument set
and records the result — keys, values and row order. With `--compare`, diffs against an
earlier snapshot and exits non-zero on any difference.

This is the method that proved HARD-19's 177 alias rewrites inert (421 keys snapshotted
before and after), made repeatable and extended from keys to values. It is how REARCH-01
and REARCH-02 prove each rewrite changes nothing, against the full local seed, which has
the real shape of real data (sanitised contacts).

- Local only: it needs `002_data.sql`, which is gitignored and holds real league data.
- Defaults to the local database, **never production** — the opposite of the other tools,
  because it calls model functions, and some model functions write. It refuses to run
  against a `supabase` host.
- Argument files live beside the package doing the conversion; they are evidence.

### Part 2 — database tests in Jest

A second Jest project, `db`, in `__tests__/db/`:

- Connects to a database called `sdbl_test` in the local container (or the CI service),
  **rebuilt from `migrations/` at the start of the run** and loaded with a **synthetic
  seed** — not `002_data.sql`, which CI cannot have and which is real data.
- Each test runs inside a transaction that is rolled back, so tests do not see each
  other's writes and need no cleanup.
- `__tests__/setup.js`'s rule stands: this project gets the local or CI connection string
  and nothing else; `testEnvGuard` already refuses a `supabase` host.

**The synthetic seed is the real work here.** It needs enough shape to exercise the
queries: two seasons with history (for REARCH-02), four divisions, a handful of clubs and
teams, players with ranks either side of the reserve line (`rank >= 99`, per the `rosters`
skill), complete and outstanding fixtures with game rows, a draft with and without a
token, a messer draft, an officer set by flag. Written as SQL or generated by a small
script; either way, committed and deterministic.

**The rule this introduces:** a model function's SQL is tested here, or not at all. A
mocked-database test of a model is not evidence that its query works. Controller tests
can keep mocking models — that is a different seam.

### Part 3 — a Postgres in CI

Cloud Build runs steps as containers on a shared Docker network. Start `postgres:17` as a
detached step (`docker run -d --network cloudbuild --name pg …`), wait for it, then run
Jest's `db` project against `pg:5432`. Keep the existing mocked step as it is.

Optionally, once that works, the Playwright suite could run in CI against the same
service: `cloudbuild.yaml`'s comment says it was kept out only "until there is a separate
database to point it at". That is a separate decision — it needs browsers in the build
image, adds minutes, and today's rule is that whoever merges runs it locally.

## Acceptance criteria

- **Part 1:** the harness reproduces HARD-19's result — run it on a function, change an
  alias to its folded form, and it reports the key difference. A demonstration, recorded.
- **Part 2:** a `db` test for `Fixture` insert that fails if `RETURNING id` is removed
  (the gotcha-2b bug, reintroduced on purpose and caught), and one for an `UPDATE`'s
  affected-row count (2d).
- **Part 3:** a CI build fails when a `db` test fails; build time recorded before and
  after.
- Cost: build minutes only — Cloud Build's free allowance covers the current volume, but
  check `gcloud builds list` durations before and after and write the numbers here. No
  runtime change.

## Out of scope

- Replacing the mocked suites. They keep testing controllers and routes; they stop being
  the only test of SQL.
- Playwright in CI (a decision, noted above).
- Regenerating `002_data.sql` (the local seed's age is a separate concern).

## Status — 25 Oct 2026

All three parts built and verified; Part 3 on Cloud Build as well (build 143a48f7, `1ffb641`,
25 Oct 2026: the `db` step ran 8 tests, 8 passed).

### Part 1 — `tools/query-snapshot.js`

Reads `dev.env` and never `.env` (`loadEnv({ localOnly: true })`), refuses any host that
is not loopback, and opens every session with `default_transaction_read_only=on`. That
goes further than the brief asked: a write function fails (`cannot execute UPDATE in a
read-only transaction`, checked with `teams.updateById`) rather than writing. Writes are
Part 2's job. Values are compared as well as keys; key *order* is not a difference, row
order is unless `--unordered`; an error is recorded as a result, so a rewrite that starts
throwing compares unequal.

**The HARD-19 demonstration.** `club.getContactDetailsById` for clubs 39, 40, 43 and a
missing id, snapshotted against the full local seed. Compared against itself: identical,
exit 0. With `venue.id AS "venueId"` folded to `AS venueId`:

```
✗ case mellor [39]
    [] (2 objects): keys only before: venueId
    [] (2 objects): keys only after:  venueid
… the same for shell and alderley …
DIFFERENT from before.json            exit 1
```

Restored afterwards. `__tests__/unit/query-snapshot.test.js` pins the host guard and the
diff rules; it needs no database, so it runs in the ordinary suite.

### Part 2 — `npm run test:db`

- `jest.db.config.js`, **not** a `projects` entry, so `npm test` and CI's first step still
  need no database. The default config ignores `__tests__/db/`.
- `__tests__/db/globalSetup.js` drops and recreates `sdbl_test` (it refuses any name not
  ending `_test`), replays `migrations/` from Node — CI's `node:22` has no `psql` — with
  `local-db.sh`'s "already exists" rule, and loads `tools/local-db/test-seed.sql`. About
  0.2 s.
- Rollback per test: `pg`'s `Pool` is replaced by `helpers/onePool.js`, one real
  connection inside a transaction per test. `db_connect.js` itself is the real module, so
  `pgify`, `[rows]` and `affectedRows` are what is tested. Each `pool.query` runs in its
  own savepoint (so a failed statement does not poison the next, as with a real pool) and
  `withTransaction`'s BEGIN/COMMIT/ROLLBACK become a savepoint. The suite tests its own
  rollback.
- The seed: three seasons (2024/25 and 2025/26 archived, the 2025/26 archive tables
  created the way the rollover makes them, with history that differs from today), four
  divisions of two teams, eight players a team including reserves at 99 and 100, officers
  by flag and one team with no captain, 18-game fixtures, a tokenless draft, a tokened
  one, a messer draft. Every NOT NULL draft column is filled from the schema, so a new
  column does not break it.

**Acceptance:** `__tests__/db/fixture.test.js`, 8 tests. Without `RETURNING id` in
`createScorecard`, 2 fail (`Received length: 0`). With `supersedeEarlierDrafts` reading
`[result, info]` / `info.rowCount`, its test fails. Each was reintroduced on purpose, seen
to fail, and restored.

### Part 3 — `cloudbuild.yaml`

`pg` (`docker run -d --network cloudbuild postgres:17`) starts in parallel with the
mocked `test` step; `pg-ready` waits on `pg_isready`; `db` runs `npm run test:db` after
both, before any image is built. Replicated locally: a clean `node:22` with `npm ci`
against a fresh `postgres:17` reached as host `pg` passed 8/8; with the bug reintroduced
`npm run test:db` exits 1, which is what fails a Cloud Build step.

**Build time before** (the 10 builds of 25 Oct 2026, 53ae3b9 … e910d89): 354–449 s in
total, median ~370 s; the `test` step 207–250 s.

**After** (build 143a48f7, `1ffb641`): 466 s in total. What this package added to the
critical path is the `db` step, **4 s**: `pg` (32 s, mostly the image pull) and `pg-ready`
(3 s) ran alongside the 236 s `test` step. The rest of the difference is elsewhere: that
commit changed `package.json`, so the image's `npm ci` layer missed the cache (docker build
40 s against the usual 5–6 s, push 33 s against ~16 s), and the deploy took 108 s, inside
its usual 84–125 s. A build that leaves `package.json` alone should come in at the old
figure plus about 4 s.
